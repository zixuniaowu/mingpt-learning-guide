Preface

In 2017, Google published "Attention Is All You Need", introducing the Transformer architecture. At that moment, few people realized it would fundamentally change natural language processing and the entire AI field.

Just two years later, OpenAI released GPT-2, a pure "guess the next word" model that showed remarkable capabilities with almost no task-specific training: writing articles, translation, Q&A, programming... People began to realize: scale + simple objective + vast data might be a path toward general intelligence.

In 2020, GPT-3 further proved this. By the end of 2022, ChatGPT took the world by storm.

But behind all of this, the core mechanism is actually very simple: an autoregressive Transformer decoder + next-token prediction + gradient descent.

minGPT is the minimal implementation Andrej Karpathy created so that anyone (especially students and researchers) can truly understand this core. It is only a few hundred lines of code, yet it faithfully reproduces all the key ideas of GPT.

This book's goal is not to teach you how to "use" large models, but to truly understand why they work, where their limits are, and what distinguishes them from other architectures.

We start from first principles, step by step:

  • What is language modeling really doing?
  • How does a model "learn" to predict?
  • What is the intuition and mathematical essence of the attention mechanism?
  • Why did GPT — not other architectures — come to dominate today's large model era?
  • What are Transformer's fundamental limitations? Where is the future going?

The book includes runnable code examples, interactive visualizations, and details from real implementations. We suggest you read alongside running the corresponding code in Jupyter Notebook.

We hope that after reading this book, when you see a model with hundreds of billions of parameters, it will no longer feel mysterious — you will clearly see it as "a very large, gradient-descent-trained, next-token-predicting Transformer".

This book is aimed at readers with basic programming and math skills (high school or early college level). All concepts are explained from first principles with concrete examples and intuitive analogies.

1. Defining a Dataset — First Principles of "Next Token Prediction" Data

The starting point of training is data. A model does not learn by magic; it learns from many examples of this form: given the previous tokens, what should the next token be?

Language modeling uses self-supervised learning: we do not need human labels because the text itself contains the labels. Shift the same token sequence by one position, and you have the training target.

Core idea: input and target differ by one position

Suppose we have a number sequence: [10, 20, 30, 40, 50, 60]. GPT is not learning to memorize this list. It is learning:

See 10, predict 20; see 10,20, predict 30; see 10,20,30, predict 40...

Written in human terms, that becomes many small questions:

Examplex (input the model sees)y (correct answer)
1[10]20
2[10, 20]30
3[10, 20, 30]40
.........

But the code does not feed these small questions one by one. For parallel training, the Dataset returns two equal-length sequences:

  • x: the token sequence the model sees
  • y: the target sequence, which is the same original sequence shifted left by one position: each position's next token

Simplest example (block_size = 5)

If block_size = 5, the Dataset first takes block_size + 1 tokens, which means 6 tokens:

chunk = [10, 20, 30, 40, 50, 60]
x = chunk[:-1]  # [10, 20, 30, 40, 50]
y = chunk[1:]   # [20, 30, 40, 50, 60]

So one training sample looks like this:

Position01234
x (input)1020304050
y (target)2030405060

This table means:

  • At position 0: seeing 10, predict 20
  • At position 1: seeing 10,20, predict 30
  • At position 2: seeing 10,20,30, predict 40
  • At position 3: seeing 10,20,30,40, predict 50
  • At position 4: seeing 10,20,30,40,50, predict 60

Notice that x does not contain 60, but y does. That is because 60 is exactly the answer the model should predict at the final position. This is the essence of next-token prediction.

One-sentence version: The Dataset does not give the model separate "question text" and "answer text". It shifts the same text by one position: x = first N tokens, y = next N tokens. The model guesses the next token at every position, and the loss tells it how wrong those guesses were.

Why does y contain -1? — A Deep Dive into the Adder Project

The simple example above is a "pure generation" task. But many real tasks are "read a question, then give the answer".

Take projects/adder as an example — a minimal experiment by Karpathy: teach GPT to do n-digit addition from scratch.

Encoding (2-digit example)

The problem 85 + 50 = 135 is encoded as the string "8550531" (length 7):

  • First 2 digits: first addend 85 → 8,5
  • Middle 2 digits: second addend 50 → 5,0
  • Last 3 digits: result encoded in reverse 135 → 5,3,1 (ones, tens, hundreds)

Important: the actual code has no + token and no = separator. The model only sees a digit string: 8 5 5 0 5 3 1.

When constructing the Dataset:

  • render = [8,5,5,0,5,3,1] (the full string)
  • x = [8,5,5,0,5,3] (drop the final digit because there is no next position for it to predict)
  • y = [5,5,0,5,3,1] (render shifted left by one position: each position's next token)

But we only want the model to learn from the answer-output positions. The earlier "reading the question" positions should not contribute to the loss.

Therefore the code sets the first 3 positions of y to the special value -1:

Position012345
x855053
Raw y to predict550531
Masked y-1-1-1531

Why reverse the result?

Reverse encoding and -1 masking are different mechanisms:

  • -1 masking decides which positions contribute to the loss. Its job is to train only on the answer part.
  • Reverse encoding decides the order in which answer digits are generated. Its job is to make the model output the answer in the natural order of the addition algorithm.

Column addition proceeds from right to left: ones, then tens, then hundreds, because carry flows from low digits to high digits.

For 85 + 50 = 135:

  • Ones: 5 + 0 = 5, so the first output digit should be 5.
  • Tens: 8 + 5 = 13, so the second output digit is 3 and carry is 1.
  • Hundreds: output the carry 1.

So the answer in computation order is 5,3,1. If we output it forward as 1,3,5, the model must predict the highest digit 1 first, but that 1 depends on carry produced by lower-digit computation. For a left-to-right GPT, that makes the task much harder.

One-sentence version: -1 controls where learning happens; reverse encoding controls the order in which answer digits are learned. After reversal, the first valid loss position is the ones digit 5, exactly the first digit addition can compute.

Diagram: Adder Data Construction with Gradient Masking

Reading the diagram clarifies the core:

  • The top row is the x the model actually "reads".
  • The bottom row — only the three green cells are valid y (the answer part the model must predict).
  • The first three red -1 positions produce loss=0, gradient=0 — the model is never penalized for whatever it predicts there.
  • This forces the model to focus its learning on "how to compute the answer from the question" rather than memorizing "what the question looks like".

Diagram: Complete Training Step Data Flow

This diagram ties the whole training workflow together: The Dataset provides correct labels only for the answer part → forward pass computes meaningful loss only at those positions → backpropagation sends gradients only to the parameters that need to learn → the model learns an algorithm, not memorization.

Why use -1 masking?

When computing the loss, we use PyTorch's F.cross_entropy(..., ignore_index=-1).

This means: when y[i] == -1, the loss at that position is 0 and no gradient flows back.

Without masking the prompt positions, the model could "cheat" — it would just memorize "when I see 85+50=, output 531" to get low loss, without ever learning the actual carry rules of addition.

With masking, the model gets no penalty for output at the first 3 positions — it must focus entirely on the last 3 positions and truly learn how to compute the result from the addends.

What happens without masking?

The model would likely memorize the whole string as a rote mapping (memorization) rather than learning a general addition algorithm. When tested on unseen number combinations, it would fail completely.

This is the profound insight of "computing loss only on the answer part": it forces the model to separate "reading the problem" from "solving the problem", and only be responsible for the solving.

In real large language model training, we use similar techniques (though in different forms). For example, in instruction tuning, we typically compute loss only on the model's generated answer, not on the user's instruction.

This is the most subtle and most easily overlooked part of the Dataset convention — it's not just "data format", it directly determines what the model actually learns.

What actually happens in one training step?

When the Trainer fetches an adder batch, the model will:

  1. See x (containing the problem and reverse-encoded answer).
  2. At every position, output a prediction for the "next token" (logits).
  3. Compute cross-entropy loss only where y is not -1 (i.e., only at the 3 answer positions).
  4. During backpropagation, gradients flow only from those 3 positions, updating model parameters to more accurately predict each digit of the answer on similar problems.

After thousands of such examples, the internal "knobs" of the model are tuned into an actual adder, not a memorization lookup table.

Comparison with standard language modeling

In standard chargpt (character-level language model), we usually compute loss on the entire sequence (except the last position).

Because language modeling has no clear separation between "reading" and "answering" — the "question" and "answer" are continuous.

In algorithmic tasks like adder, we must artificially create this separation, otherwise the model learns memorization instead of algorithm.

This idea remains critical in today's large model era: through carefully constructed instruction data + loss only on the answer part, we teach models to "follow instructions" rather than "regurgitate instructions".

Part 1: Language Modeling & Learning from First Principles

We start from zero, using concrete examples to explain "text → numbers → model thinking → next word prediction".

1. What is Language Modeling Really Doing? — The "Always Guess the Next Word" Game

Have you ever played the "word chain" game? Someone says "I like" and you immediately reply "cats" or "dogs" or "pizza".

This is exactly what GPT does, taken to the extreme: given all the preceding words, it scores each possible "next word".

It's not "understanding meaning" — it's learning statistical patterns from vast amounts of text: "after 'I like', 'cats' appears much more often than 'airplanes'".

2. First Principles of Language Modeling and Learning

So far, we've said "the model's job is to guess the next word". But how does it go from "completely unable to guess" to "able to guess"?

This involves three core mechanisms at the heart of AI. Let's start from first principles.

Any learning system has only three things

Whether it's a person learning basketball or a neural network learning word prediction, it's essentially a three-step cycle:

  1. Make a guess (Forward pass)
  2. Measure how wrong the guess is (Compute Loss)
  3. Based on how wrong you are, slightly adjust the internal "knobs" to do better next time (Gradient descent + parameter update)

The model has thousands of "knobs" (those weight parameters). Training is repeatedly turning these knobs so it makes fewer errors on similar problems.

Loss Function: The Error Scorer

The loss function is an "error scorer". Its only job is to give the current guess a score — lower is better.

For "guess the next word" tasks, we use Cross Entropy Loss.

Intuition:

The model assigns a probability to each possible word (summing to 1). If it gives high probability to the "correct answer", loss is low. If it gives low probability to the correct answer (it's "surprised"), loss is high.

Here's a minimal example (3 possible words A, B, C, correct answer is B):

Model's probabilitiesConfidence in BLoss (intuition)
[0.1, 0.8, 0.1]Very high (80% for B)Very small ✓
[0.3, 0.4, 0.3]MediumMedium
[0.6, 0.2, 0.2]Low (only 20% for B)Very large ✗

In minGPT's code, this is the line that computes loss:

loss = F.cross_entropy(
    logits.view(-1, vocab_size),   # model's raw scores
    targets.view(-1),              # correct answer token IDs
    ignore_index=-1
)

Internally, it first converts logits to probabilities (softmax), then computes "the lower the probability of the correct answer, the higher the loss".

Gradient Descent: How do we know which knob to turn?

Now we know how wrong we are (the loss value). But with hundreds of thousands or even billions of knobs in the model, which one should we turn, and in which direction?

The answer is the gradient.

Imagine the loss as a mountain (higher = bigger error). We're standing on the hillside and want to reach the valley (loss = 0).

The gradient tells us: "at your current position, if you turn a particular knob slightly, does the mountain get higher or lower? And by how much?"

Gradient descent works by: always taking a small step in the direction that makes the mountain lower (reduces loss) the fastest.

The step size is controlled by the learning rate. Too large and you might overshoot the valley; too small and it takes forever.

Classic Visualization: Loss Landscape

The most famous gradient descent visualization draws the loss as a 3D surface (a "bowl" or "valley"), with a small ball (representing current parameters) rolling on it.

Below is an interactive simplified version (2D). You can adjust the learning rate and watch the ball "roll down the hill":

Red curve = loss function (simple quadratic f(x)=x²). Blue dot = current parameter position. Green arrow = gradient direction (towards increasing loss). Each "step" moves the dot along the negative gradient direction.
Small LR: slowly rolls down (stable but slow). Large LR: may overshoot and oscillate. Adding momentum smooths the path, like a ball with inertia.

How to read this interactive diagram:

  • Red curve = loss function (parabola, lower in the middle = smaller loss). This is "how wrong the model currently is".
  • Red ball = your current parameter position (billions of dimensions in reality, simplified to 1D here).
  • Green arrow = gradient direction (fastest increase direction). We always move in the opposite direction (downhill).
  • Drag the "learning rate" slider to see the ball's behavior change: too small = slow crawl; too large = overshoot and oscillation.
  • Turn on "momentum" and the ball carries inertia, making the path noticeably smoother and faster (that's why modern optimizers add momentum).

In real GPT training, the loss landscape is a "super complex mountain range" with billions of dimensions. AdamW adapts both step size and momentum per dimension, letting the ball find the valley faster and more stably.

This is why we say "gradient descent = keep moving parameters in the direction that reduces loss the fastest". Backward propagation (loss.backward()) computes this "fastest descent direction" (gradient), and optimizer.step() actually moves the parameters.

Backpropagation: Automatic gradient computation

Manually computing the gradient for each knob is nearly impossible. Fortunately, PyTorch provides loss.backward().

It uses the Chain Rule to automatically compute "backwards" from the loss: which layer is to blame? Which parameter? By how much?

This process of "pushing responsibility backwards" from the output error is called Backpropagation.

Imagine a very simple two-layer neural network:

Input → Hidden layer (weights W1) → Output layer (weights W2) → Loss

When we get the loss, backpropagation first asks: "Who is mainly responsible for the output layer's error?" (mostly W2).

Then passes this "error signal" to the hidden layer: "Who is mainly responsible for the hidden layer's error?" (W1).

Finally, all error signals become gradients for each weight.

Figure: Backpropagation "responsibility distribution" diagram

Reading this diagram: After the loss is computed at the far right, the error signal travels backward like "distributing blame". Each layer takes a share of responsibility, which ultimately becomes the gradient for each weight.

This is why we say "the gradient is the partial derivative of the error with respect to the parameter" — it precisely quantifies "if I change this parameter by a tiny amount, how much will the loss change".

How does it work in the actual training loop?

Look at the core loop in Trainer (we'll have a complete mini-experiment later):

logits, loss = model(x, y)            # 1. Forward: make prediction + compute loss
model.zero_grad(set_to_none=True)
loss.backward()                       # 2. Backward: compute gradients for each knob
optimizer.step()                      # 3. Update: actually turn the knobs

Diagram: Training Cycle Visualization

Repeat this loop thousands of times, and the model's internal knobs gradually adjust to a position where it guesses more accurately on the training data.

First Principles Summary:
Training = repeatedly doing "predict → score (loss) → find fastest descent direction (gradient) → take a small step (update parameters)".
The loss function tells you "how wrong you are", gradient descent tells you "where to change", and backpropagation automates the whole process.

Now you understand the three most essential components of "learning". Later, when we look at the actual code, we'll keep coming back to these three concepts.

3. The Evolution of Sequence Modeling: From RNN to Transformer

To truly understand why GPT chose the Transformer, we must first understand how people processed sequential data before, and what fundamental problems those methods encountered.

The Era of RNNs

In the early days of deep learning, the most common model for text was the Recurrent Neural Network (RNN).

Core idea: Use the same "cell" to process each element of the sequence in order, while maintaining a "hidden state" that carries a summary of all preceding information.

Analogy: As you read a book, you continuously update your mental state of "where I am in the story".

The math of RNNs is simple:

hₜ = tanh(Wₕₕ · hₜ₋₁ + Wₓₕ · xₜ + b)

Problems quickly emerged:

  • Vanishing/exploding gradients: When sequences are long, backpropagation must travel through many time steps. Gradients either vanish (early information is completely lost) or explode (training crashes).
  • No parallelism: Must compute strictly sequentially — step t depends on step t-1. Very inefficient on GPUs.
  • Long-range dependency difficulties: The model struggles to remember information from 50 steps ago.

LSTM and GRU Improvements

To solve the vanishing gradient problem, researchers proposed LSTM (Long Short-Term Memory) and later GRU.

They introduced "gating" mechanisms (forget gate, input gate, output gate), allowing the model to selectively remember or forget information.

This was a huge leap forward — many speech recognition and machine translation systems achieved state-of-the-art results with LSTM.

But fundamental problems remained:

  • Still sequential computation, unable to fully exploit modern hardware parallelism.
  • Although gradient vanishing was mitigated, long-range dependencies remained fragile.
  • Model complexity was high, making both training and inference slow.

The Seq2Seq + Attention Transition

In 2014, the Seq2Seq model was proposed: one RNN encodes the input into a fixed vector, another RNN decodes to generate the output.

This was very successful for machine translation. But it was soon discovered that compressing the entire input into a single vector was a bottleneck.

Then Bahdanau Attention (2014) and Luong Attention emerged.

Key breakthrough: During decoding, instead of looking at just one fixed vector, the model can "dynamically attend" to different parts of the input sequence.

At this point, attention was only an auxiliary module for RNN, not the main character.

2017: Attention Is All You Need

Google's paper made the boldest decision: throw away recurrence entirely, use only attention.

They proposed Self-Attention: every position in the sequence can directly compute relevance with every other position, without sequential information passing.

This brought revolutionary advantages:

DimensionRNN/LSTMTransformer (Self-Attention)
ParallelismVery poor (must be sequential)Excellent (all positions simultaneously)
Long-range dependenciesDifficultDirect (any distance is O(1) path)
Compute complexity (seq len n)O(n)O(n²) (but small constant, actually faster)
InterpretabilityPoorAttention weights directly visualizable

Transformer immediately surpassed previous SOTA on machine translation, with training speed an order of magnitude faster.

This laid the foundation for GPT, BERT, T5, and all modern large models.

As it turns out, for the extremely general pre-training objective of "next word prediction", pure Decoder + autoregressive generation is the simplest and most effective: you train it with "predict next word", and generate using the exact same "predict next word" mechanism — training and inference objectives are naturally aligned. BERT's bidirectional attention sees more context, but its training (masked filling) and inference (understanding) are not fully consistent, and it's less natural as a generative model.

Comparison with Vision Transformer (ViT)

Transformer has not only dominated NLP but also entered computer vision. ViT cuts images into patches and treats them as sequences.

Key differences:

  • Vision has no natural "causal" order, so ViT uses bidirectional attention + position encoding.
  • But in video generation or autoregressive image generation, people start using GPT-like causal versions (e.g., ImageGPT).
  • This shows that the attention mechanism is very general; whether to use causal or bidirectional is mainly determined by the "generation vs understanding" nature of the task.
What history teaches us: Many seemingly complex advances are actually the result of removing inductive biases and letting the model learn from data. RNNs have strong sequential inductive biases; Transformer has almost none, leaving everything for attention to discover. The success across vision and language further proves this point.

4. From Words to Vectors: Tokenization & Embedding

Computers only understand 0s and 1s. Text must first be translated into integers.

The simplest approach would be "one number per letter" — but that makes sequences too long, forcing the model to learn spelling rules.

GPT-2 uses a smarter method called BPE (Byte Pair Encoding):

  • First split sentences into chunks using spaces and punctuation.
  • Map each byte to a nice visible symbol (space becomes Ġ).
  • Then use a trained merge table to combine common byte pairs into subwords. GPT-2's final vocabulary has about 50k tokens.

Result: common words (like "like") get their own token, while rare words get split. You can try this yourself in the later BPE section with real code.

Step 1: Text → Integer IDs

After BPE, "I like cats" becomes [40, 588, 11875] — three integers. These integers are all the model ever sees. It never processes letters directly.

Step 2: Integers → "Flavorful Vectors" (Embedding)

Now we have a sequence of integers: [40, 588, 11875]. The model must "translate" each integer into a vector of length 48 (gpt-nano) or 768 (GPT-2).

Think of this vector as the word's "ID card + personality description":

  • ID 40 ("I") → a 768-dim vector
  • ID 588 ("like") → another vector

Initially these vectors are random (like a newborn who has no concept of words). During training, the model slowly adjusts them so that semantically similar words end up with similar vectors.

Important: Position information must be added too!

If we only had word vectors, the model would confuse order: "I like cats" and "cats like I" have the same words.

So we also add a "what position am I in" vector (Position Embedding) at each position, then add the two vectors together.

Now every position has a vector that "knows both what token it is and which step it stands at".

The most important shape change (remember with this tiny example):
Input: 2 sentences, 3 words each → shape (2, 3)
After word embedding + position embedding → (2, 3, 48) ← 48 is gpt-nano's "brain capacity"
After all Transformer layers: still (2, 3, 48)
Final output → (2, 3, 50257) ← each position scores all 50k+ possible next words

6. Self-Attention: The Core of Transformer

Self-attention is the fundamental innovation that distinguishes Transformer from all previous sequence models. It allows each position to directly "see" the relationship with any other position, without the sequential information passing required by RNNs.

First Principles: Why Do We Need Attention?

Imagine reading: "I went to the bank to deposit money because I need to pay rent." When you read "pay", you need to recall what "rent" is and why you went to the "bank". Your brain automatically associates "pay" with "rent" and "bank" with "deposit".

RNNs can only compress all previous information into one hidden state, easily losing details. Attention allows each word to directly "query" all other words and decide what to focus on.

The Self-Attention Computation (Intuition + Math)

Self-attention can be broken into three concepts: Query, Key, Value.

  • Query (Q): What does the current word want to ask? ("Who should I pay attention to?")
  • Key (K): What information can other words provide? ("What do I have?")
  • Value (V): The actual content of other words.

Computation steps:

  1. Transform input vectors through three linear layers to get Q, K, V.
  2. Compute similarity (dot product) between Q and all K, yielding attention scores.
  3. Scale by 1/√d_k (prevents softmax gradient vanishing from large values).
  4. Apply causal mask in GPT (upper triangle set to -∞), ensuring no peeking into the future.
  5. Softmax converts scores to probability weights.
  6. Weighted sum of V produces the new representation for the current position.
Attention(Q, K, V) = softmax( (Q K^T) / √d_k + Mask ) V

Multi-Head Attention

A single attention head can only learn one "attention pattern". Multi-head attention splits Q/K/V into multiple subspaces, letting different heads learn different relationships in parallel:

  • One head might focus on subject-verb grammatical relationships.
  • Another head might focus on semantic "causal" relationships.
  • Yet another head might focus on nearby positional relationships.

Finally, all head outputs are concatenated and fused through a linear layer.

After 2023, Mamba, RWKV, RetNet and other architectures aim to solve Transformer's O(n²) problem.

  • Mamba: Uses selective state space models (SSM), reducing complexity to O(n), with significant speed and memory advantages on long sequences.
  • RWKV: Reformulates attention as a linear RNN — trains like a Transformer, infers like an RNN.
  • RetNet: Proposes parallel, recurrent, and chunk-wise recurrent modes, balancing training efficiency and inference speed.

Currently, these models approach or match similarly-sized Transformers on some long-context benchmarks, but still lag slightly in general capability. Hybrid architectures (Transformer + Mamba blocks) are becoming a new trend.

Attention as "Soft Dictionary Lookup"

Another useful intuition is to think of attention as a differentiable, soft dictionary lookup.

In traditional programming, you use a key to look up a hash table and get the exact value. Attention lets you use a Query to compare similarity with all Keys, then mix all Values weighted by similarity.

This allows the model to extract information "on demand" from the context, rather than compressing all history into a fixed-size vector like RNNs.

In GPT, because it's causal, this "dictionary" can only contain current and prior positions — perfectly matching autoregressive generation.

Different "Experts" in Multi-Head Attention

In trained GPT models, different attention heads often learn distinctly different behaviors:

  • Some heads mainly focus on local context (neighboring tokens).
  • Some heads focus on long-range syntactic dependencies (subject-verb agreement).
  • Some heads perform "copying" behavior (directly copying a previous token).
  • In code generation, some heads specifically track indentation and bracket matching.

This "division of labor" emerges automatically during training, not by design. This is why multi-head attention is much stronger than single-head.

Causal Mask Importance

GPT uses "causal self-attention", meaning position i can only see positions ≤ i. This ensures autoregressive correctness: when generating token t, the model absolutely cannot "peek" at future content.

Compare with BERT's bidirectional attention (can see the entire sentence) — this is why BERT cannot be directly used for generation.

Trace Through Attention with a Concrete 3-token Example

Let's use a simple 3-token example: "I like cats" (positions 0, 1, 2)

When the model processes position 1 ("like"), it can look at "I" and itself, but it must avoid "cats" because that future token has not appeared yet.

Below we break the attention mechanism into 5 small steps, each with an intuitive analogy.

Analogy:
Imagine you're a detective reading a diary.
• You (current position) want to know "which previous information should I focus on".
• You first ask yourself: "What information do I need?" → This is Query (Q)
• Then you look at each previous person: "What information can you provide?" → This is Key (K)
• What each person actually provides → Value (V)
• You vote (weight) based on match quality, then mix their provided content proportionally.
• Most importantly: you absolutely cannot peek at future parts that haven't been written yet → This is the causal mask!

Five-Step Computation

  1. Step 1: Transform input into Q, K, V
    Through a linear layer called c_attn, each position's vector is simultaneously transformed into three versions. Like photocopying a person's resume three times, labeling them "what I want to ask", "what I can answer", "what I actually know".
  2. Step 2: Compute "match scores"
    Dot product each position's Q with all positions' K. Higher score means "this person has what I need right now".
  3. Step 3: Scale + causal mask (the most critical step!)
    First divide by √head_dim to prevent numeric explosion. Then fill all "future" positions with a very large negative number (-∞). When softmax runs, future positions will have probability 0.
  4. Step 4: Softmax → "attention weights"
    Convert scores to a 0-1 probability distribution summing to 1. Like converting match scores into "how much attention I should pay to this person".
  5. Step 5: Weighted sum → output
    Multiply weights with corresponding V vectors and sum them up. The result is a new vector that "combines all relevant context information".
Attention(Q,K,V) = softmax( (Q @ Kᵀ) / √d + causal mask ) @ V

q, k, v = self.c_attn(x).split(self.n_embd, dim=2)
k = k.view(B, T, self.n_head, C // self.n_head).transpose(1, 2)
q = q.view(B, T, self.n_head, C // self.n_head).transpose(1, 2)
v = v.view(B, T, self.n_head, C // self.n_head).transpose(1, 2)

7. Transformer Block

Each Block contains two sublayers, organized with residual connections and Pre-LayerNorm (GPT-2 style).

Figure: Transformer Block Internal Structure

This diagram shows the data flow through a single Block:

  • Input x_in first passes through ln_1 (LayerNorm), then enters Causal Self-Attention.
  • Attention output is added to the original input via residual connection (+ symbol).
  • Then passes through ln_2, then MLP (linear expansion to 4× dimensions + GELU activation, then linear contraction back + Dropout).
  • Finally, another residual addition produces x_out.

Residual connections let gradients "short-circuit" back to earlier layers, solving deep network training difficulties. Pre-LN (normalization before sublayer) is more stable than early Post-LN, which is why modern models like LLaMA continue to use similar designs (replacing LayerNorm with RMSNorm).

x = x + Attention(LN(x))
x = x + MLP(LN(x))

Why is the Transformer Block Designed This Way?

Think of a Block as "a smart meeting room":

  • LayerNorm = "First adjust everyone's speaking volume to a similar level" (keep values reasonable)
  • Attention = "Everyone can ask questions and listen to others" (information exchange)
  • Residual connection = "After the meeting, take your original notes with you" (don't forget what you wanted to say)
  • MLP = "Everyone returns to their office to think more deeply" (non-linear transformation, enhanced expressiveness)
  • 4× expansion = gives each person a larger whiteboard to think with

Pre-LayerNorm (normalize before doing things) is more stable than old Post-LN — like "calm down and drink some water before discussing".

FFN's 4× Expansion — Why Does It Work?

The feed-forward network (MLP) in a Block expands from n_embd to 4×n_embd then contracts back — this is GPT's classic design.

From first principles:

  • This gives each position a "small expert network" to perform complex non-linear transformations in a higher-dimensional space.
  • The 4× multiplier is a "sweet spot" validated by extensive experiments: too small and expressiveness suffers, too large and parameters/computation are wasted.
  • Later LLaMA replaced GELU with SwiGLU, further improving this "expert network's" efficiency.

Block Design Evolution and Modern Variants

From GPT-2's classic Block to today, researchers have made many tweaks, but the core "Pre-LN + residual + Attention + FFN" structure is remarkably resilient.

  • LLaMA uses RMSNorm + SwiGLU, replacing LayerNorm + GELU — more stable training, stronger expressiveness.
  • Mistral adds Sliding Window + GQA to attention.
  • Some experiments swap the order of Attention and FFN, or add more residual branches.

But no matter what changes, the first principle "residual connections make deep networks trainable" never changes. minGPT's simple implementation lets you see the elegance of this structure clearly.

Design Points (Simplified)

  • Residual connections are the most important: they make very deep networks trainable (like a highway where each layer can choose "do nothing and just pass through")
  • Each layer doesn't do much, but stacking 12, 24, 48 layers becomes very powerful
  • Dropout is "intentionally closing your eyes sometimes" to prevent the model from relying too heavily on any single piece of information

Why Pre-LN is More Stable Than Post-LN

Applying LayerNorm before the residual connection stabilizes each layer's input distribution, preventing gradients from quickly vanishing or exploding as depth increases. This is the fundamental reason all large models since GPT-2 use Pre-LN (or RMSNorm).

Architecture Evolution: Code-Level Deep Dive

minGPT uses GPT-2's classic design. Modern models (LLaMA, Mistral, DeepSeek) have evolved each component. Below we compare the implementations side by side.

RMSNorm vs LayerNorm

LayerNorm normalizes by both mean and variance. RMSNorm removes the mean-centering step, using only RMS (root mean square). This is simpler, faster, and empirically equally effective:

# LayerNorm (GPT-2 / minGPT) — normalizes mean AND variance
mean = x.mean(-1, keepdim=True)           # compute mean
var = x.var(-1, keepdim=True, unbiased=False)  # compute variance
x_norm = (x - mean) / torch.sqrt(var + eps)    # center + scale
y = x_norm * gamma + beta                 # affine transform

# RMSNorm (LLaMA / modern) — only RMS, no mean-centering
rms = torch.sqrt((x.pow(2)).mean(-1, keepdim=True) + eps)
x_norm = x / rms                          # scale only
y = x_norm * gamma                        # no beta (usually)

The practical impact: RMSNorm saves the mean computation, reduces one all-reduce in distributed settings, and provides slightly better training stability at scale. LLaMA, Mistral, Gemma, DeepSeek all use RMSNorm.

SwiGLU vs GELU

GELU is a smooth approximation of ReLU. SwiGLU (Swish-Gated Linear Unit) introduces a gating mechanism: the output is the element-wise product of two linear projections, one activated by Swish (SiLU). This adds an extra nonlinear interaction between dimensions:

# GELU (minGPT / GPT-2) — simple nonlinear activation
x = linear_proj(x)          # project to 4*n_embd
x = GELU(x)                 # smooth activation
x = linear_proj(x)          # project back to n_embd

# SwiGLU (LLaMA / modern) — gated nonlinear activation
x_gate = linear_gate(x)     # gate projection
x_value = linear_value(x)   # value projection
x = Swish(x_gate) * x_value # gated: element-wise multiply
x = linear_proj(x)          # project back to n_embd

SwiGLU was shown to consistently outperform GELU at the same parameter count. Note that SwiGLU's intermediate dimension is typically 8/3 * n_embd (not 4x), since the gating already adds parameters. LLaMA, Mistral, PaLM, and DeepSeek all adopted SwiGLU or its variants.

From MHA to GQA: The KV Cache Evolution

Standard Multi-Head Attention (MHA) gives each head independent K and V. During inference, this explodes the KV cache (n_layers × 2 × n_heads × head_dim × seq_len). GQA (Grouped Query Attention) shares K/V heads across query groups:

# MHA (minGPT) — each query head has its own K,V
k = k.view(B, T, n_head, hs).transpose(1, 2)  # n_head K,V heads
v = v.view(B, T, n_head, hs).transpose(1, 2)
# KV cache size per layer: 2 * n_head * hs * seq_len

# GQA (LLaMA2+) — query heads share K,V groups
n_kv_heads = n_head // kv_groups              # e.g., 8 queries → 2 KV groups
k = k.view(B, T, n_kv_heads, hs).transpose(1, 2)
v = v.view(B, T, n_kv_heads, hs).transpose(1, 2)
# KV cache size per layer: 2 * n_kv_heads * hs * seq_len
# Memory saving: 4x if n_head=32, n_kv_heads=8

This seemingly small change is critical for long-context inference: it directly reduces the memory footprint by a factor of 4-8x, making 128k+ context windows feasible in practice. LLaMA2-70B, Mistral-7B, and GPT-4 all use GQA or MQA.

Each colored block represents a KV head cached in memory. GQA shares KV heads across query groups; MQA shares a single KV head across all queries. This is the single biggest optimization enabling long-context inference.

GELU is the activation function chosen by GPT-2. It is smoother than ReLU and does not completely truncate small negative values.

12. BPE Tokenizer (Byte Pair Encoding)

BPE encodes arbitrary UTF-8 text into integer sequences. It's the tokenization scheme used by GPT-2, with a vocabulary size of 50,257.

Figure: BPE Tokenization Flow

This diagram shows the four main steps from raw text to final token IDs:

  1. Regex pre-tokenization: split the sentence into coarse-grained pieces by spaces, punctuation, apostrophes, etc.
  2. Byte mapping (bytes→unicode): map each UTF-8 byte to a "displayable" Unicode character (space becomes Ġ).
  3. BPE merges: apply trained merge rules bottom-up, merging frequent byte pairs into subwords.
  4. Obtain final token IDs for Transformer input.

Compared to BERT's WordPiece or LLaMA's SentencePiece, GPT-2 BPE's hallmark is encoding leading spaces into tokens (Ġ), allowing the model to better distinguish word boundaries. Byte-level schemes (like ByT5) skip the merge step entirely but produce longer sequences.

Encoding Flow

  1. Pre-tokenization: Use regex to split text into word pieces (handling spaces, punctuation, etc.)
  2. Byte mapping: Map each byte (0-255) to a printable Unicode character (avoid invisible characters)
  3. BPE merges: Apply trained merge ranks, iteratively merging the highest-priority byte pairs
  4. Lookup: Look up merged tokens in encoder.json vocabulary to get integer IDs

Comparison with WordPiece, SentencePiece, Unigram

BPE is not the only subword tokenization method. Different model families chose different schemes:

  • WordPiece (BERT): Similar to BPE, but merges based on likelihood gain for the language model rather than pure frequency.
  • SentencePiece (T5, LLaMA, Mistral): Operates directly on Unicode characters, no need for regex pre-tokenization. More natural for multilingual support. LLaMA series uses SentencePiece + BPE algorithm.
  • Unigram LM: Starts with a large vocabulary and progressively removes tokens that contribute least to the language model (probabilistic perspective).

These methods have tradeoffs in vocabulary size (typically 30k-128k) and handling of rare words. But the core idea is the same: use a limited number of tokens to cover natural language statistics while remaining reversible.

How the Tokenizer Affects Model Capabilities (First Principles)

The tokenizer is the model's first "perceptual filter" on the world:

  • If the tokenizer splits "artificial intelligence" into many small pieces, the model needs more layers to learn the concept.
  • A code tokenizer sensitive to indentation and brackets makes code tasks easier to learn.
  • Multilingual model tokenizers must balance token efficiency across languages.

Modern models increasingly emphasize tokenizer training (more data, better algorithms) because it directly impacts the model's "perception granularity" and final performance ceiling.

13. The Essence of Training: From Loss to Parameter Updates

In earlier chapters, we understood learning from first principles as "predict → score → adjust". This chapter expands every detail of this process in GPT training, comparing with industrial practice and other optimization methods.

Deeper Understanding of the Loss Function

In language modeling, we almost always use Cross Entropy Loss.

From an information theory perspective, it measures the KL divergence between "the model's predicted distribution" and "the true next-word one-hot distribution".

Why not use MSE (Mean Squared Error)? Because for classification, MSE's penalty on probabilities isn't "sharp" enough. Cross entropy gives very large gradients when the model has low confidence in the correct answer, pushing the model to correct quickly.

In code:

loss = F.cross_entropy(logits.view(-1, vocab_size), targets.view(-1), ignore_index=-1)

ignore_index=-1 is a very practical trick. In the adder project, it masks out the "problem part" from loss, so the model only learns from the "answer part".

Gradient Descent and Optimizers

The simplest gradient descent is:

θ ← θ - η · ∇L

where η is the learning rate.

In practice, we use AdamW (GPT's standard):

  • Momentum: Makes update direction more stable, less oscillation on steep loss surfaces.
  • Adaptive learning rate: Smaller steps for frequently updated parameters, larger steps for rare parameters.
  • Weight Decay: Apply L2 regularization only to weight matrices, not to bias and LayerNorm parameters (key difference between AdamW and Adam).

In minGPT's configure_optimizers, parameters are explicitly divided into two groups:

  • decay group: Linear layer weights
  • no_decay group: bias, LayerNorm, Embedding weights

Gradient Clipping

In Transformer training, gradients can easily explode in certain layers. minGPT uses clip_grad_norm_(model.parameters(), 1.0), clipping the global gradient norm to 1.0.

This is one of the simplest and most effective tricks for stabilizing large model training.

Loss Landscape: Why Learning Rate Choice Matters

Imagine the loss function as a mountainous terrain. The model's parameters are a ball placed somewhere on this terrain, and training is rolling the ball downhill to find the lowest valley.

The diagram above illustrates a cross-section of the loss landscape. Three scenarios:

  • Too small LR (red): The ball barely creeps downhill and gets stuck on a shallow slope. Training progresses extremely slowly and may never reach the valley. In practice: loss decreases very slowly, plateauing at a high value.
  • Just right LR (green): The ball smoothly rolls down into the valley. This is what a well-tuned learning rate looks like — loss decreases steadily and reaches a good minimum.
  • Too large LR (orange): The ball has so much momentum it bounces out of the valley and overshoots. In training, this manifests as loss spikes — sudden explosions in loss value. This is why gradient clipping exists: it prevents the "ball" from jumping too far when the gradient is unusually large.

Why warmup helps: At initialization, the model's parameters are random and the loss landscape near the starting point is extremely steep and chaotic. A large step in the wrong direction can permanently destabilize training. Warmup starts with tiny steps, letting the model find its bearings before full-speed gradient descent.

Learning Rate Scheduling

Modern LLM training almost always uses Warmup + Cosine Decay or WSD (Warmup-Stable-Decay) scheduling.

  • Warmup: Linearly increase learning rate from 0 to peak over the first few thousand steps, preventing early instability.
  • Cosine Decay: Smoothly decrease learning rate to a very small value.
  • Stable phase: For very large models, there's a phase where learning rate stays constant.

Understanding AdamW Hyperparameters: betas=(0.9, 0.95)

The two beta values in AdamW control very different aspects of optimization:

  • beta1=0.9 (momentum): Think of a ball rolling down a hill. 0.9 means "90% of the previous direction + 10% of the new gradient." Higher beta1 (0.95) = smoother, less noisy trajectory, but slower to change direction. Lower (0.8) = more responsive but jittery. 0.9 is the default because it balances smoothness with responsiveness for most LLM training.
  • beta2=0.95 (adaptive LR): This controls how far back Adam looks to estimate the "typical gradient size" per parameter. It's an exponential moving average of squared gradients. beta2=0.95 means it considers roughly the last 20 steps when estimating variance. Higher (0.999) = more stable estimates but slow to adapt when gradient statistics change. Lower (0.9) = faster adaptation but noisier.

Intuition cheat sheet: beta1 controls the direction memory (which way are we going), beta2 controls the step size memory (how big should each parameter's steps be). If training oscillates wildly, increase beta1. If loss plateaus early, decrease beta2.

Why AdamW and not Adam? Adam has a bug: the weight decay is applied inside the adaptive learning rate, so parameters with large gradients get regularized more heavily. AdamW decouples weight decay from the adaptive LR, applying it directly to the weights. This small fix significantly improves generalization, especially for LLMs.

Data is Half of Training (First Principles)

Many people focus only on model architecture and optimizers, but data quality is often more important than model size. From first principles, the model is just a "function approximator" — what it can fit depends entirely on what data you show it.

In the Scaling Laws era, we've learned:

  • High-quality, clean, diverse data makes models of the same size perform better (Chinchilla paper's core finding).
  • Data repetition harms performance, even leading to "memorization" rather than "generalization".
  • Data mixing ratios (code, web, books, dialogue, math) need careful tuning. Different ratios produce vastly different capability profiles.

Concrete example: Same architecture, different data

Consider training the exact same gpt-nano model on two different datasets:

  • Dataset A: 100MB of cleaned Wikipedia text. The model will learn good grammar, factual knowledge, and coherent paragraph structure. But it will struggle with code, math, or dialogue.
  • Dataset B: 100MB of GitHub Python code. The same model will learn indentation patterns, function call syntax, and variable naming conventions. But it will produce gibberish if asked to write prose.
  • Dataset C (mixed): 50MB Wikipedia + 50MB GitHub. The model will be "okay at both but expert at neither" — unless the total dataset is large enough for the model to learn both distributions. This is why Chinchilla's findings are critical: you need sufficient tokens for each domain.

Practical advice for minGPT experiments: If your minGPT model isn't learning, the first thing to check is not the architecture — it's your data. Are the (x, y) pairs correctly aligned? Does the vocabulary cover your text? Is there enough diversity? A perfect Transformer with bad data will produce perfect-looking garbage. The "garbage in, garbage out" principle is amplified in language models because they will fluently generate plausible-sounding nonsense.

Experiment idea: Train the same minGPT model on Shakespeare vs. Python code vs. random numbers. The architecture never changes, but the model will learn completely different patterns. This is the most direct way to internalize "data is half of training."

Training Stability: Small vs Large Models

Training a few-million-parameter minGPT vs a 70B model are engineering-wise two completely different worlds.

  • Small models (minGPT level) almost never worry about loss spikes. Random init + normal AdamW works.
  • Large models need a series of "black magic" techniques: precise initialization scaling (GPT-2's residual projection init 1/sqrt(2N)), QKV bias set to 0, LayerNorm epsilon tuning, gradient clipping to 1.0, loss scaling, BF16 master weight protection, selective weight decay, etc.
  • When a loss spike happens, you often need to roll back to the previous checkpoint and adjust hyperparameters, or even redesign initialization.

These "details" are deliberately omitted from minGPT because its goal is education. The pitfalls you don't see in small experiments will kill you in real large model training.

14. Autoregressive Generation

model.generate() implements autoregressive generation: predict one token at a time, append to sequence, repeat until reaching the desired length.

The generation flow:

  1. prompt: initial input sequence.
  2. forward: model forward pass, get logits at the last position.
  3. logits/T: apply temperature scaling (controls randomness).
  4. sample: based on temperature and top-k/top-p, sample the next token (or greedy argmax).
  5. append: concatenate new token to sequence, repeat until max_new_tokens reached.

Unlike BERT (one-shot bidirectional understanding), GPT's generation must be strictly autoregressive, making the causal mask essential. Production Transformers usually maintain a KV cache to avoid recomputing old tokens. minGPT's teaching implementation is simpler: it does not use a KV cache, so each generation step runs a fresh forward pass over the current context.

15. Fine-Tuning: Adapting Pretrained Models

By now you understand how GPT is trained from scratch. But in practice, almost nobody trains a foundation model from scratch. Instead, they take an existing pretrained model and fine-tune it — continue training on a smaller, targeted dataset to adapt the model for a specific task or domain.

What Is Fine-Tuning?

Fine-tuning means taking a model that already knows "how to speak" (pretrained on billions of tokens) and teaching it "what to say" in your specific context. The pretrained model has learned grammar, world knowledge, reasoning patterns, and general language understanding. Fine-tuning reshapes this knowledge toward a particular goal.

From first principles: pretraining gives the model a good initialization — it's already in a "valley" of the loss landscape that corresponds to coherent language. Fine-tuning moves the model from that general valley into a more specific valley that matches your domain. Because you start from a good point, you need far less data and compute compared to training from scratch.

Key intuition: Pretraining = learn to speak any language. Fine-tuning = learn to speak your specific dialect. The model doesn't "forget" how language works; it just adjusts its priorities.

Full Fine-Tuning

Update all model parameters on your target dataset. This gives the maximum flexibility — every layer can adapt to the new domain. But it's expensive:

  • A 7B model in FP32 requires ~56GB of GPU memory just for the parameters (without optimizer states).
  • With AdamW optimizer, you need ~112GB for optimizer states (2x momentum + 2x variance per parameter).
  • Plus activations, gradients, and batch data. Total: easily 200GB+ for a 7B model.

Full fine-tuning also risks catastrophic forgetting — the model may lose its general capabilities if over-trained on a narrow domain.

LoRA (Low-Rank Adaptation)

LoRA is the most popular parameter-efficient fine-tuning method. Instead of updating the full weight matrix W (which might be 4096×4096), LoRA adds a small "bypass" path:

W' = W + BA, where B ∈ ℝ^{d×r}, A ∈ ℝ^{r×k}, r ≪ min(d,k)

The original W is frozen (no gradient computed). Only the tiny matrices A and B are trained. For a 4096×4096 layer with rank r=8, LoRA trains only 4096×8 + 8×4096 = 65,536 parameters instead of 4096×4096 = 16,777,216 — a 256× reduction.

During training, W stays frozen and A/B update. During inference, you can merge them: W_merged = W + BA (zero additional cost). Or keep them separate for quick task switching.

LoRA best practices:

  • Rank r: 8-64 for most tasks. Higher rank = more capacity but diminishing returns. r=16 is a good default.
  • Target modules: Apply LoRA to attention projection matrices (Q, K, V, O) for best results. Adding MLP layers helps for domain-specific tasks.
  • Alpha scaling: The LoRA update is scaled by alpha/r. alpha=16 with r=8 gives a scale of 2. Start with alpha = 2× rank.

QLoRA: LoRA + Quantization

QLoRA pushes efficiency further by quantizing the frozen base model to 4-bit (NF4 format) while keeping LoRA adapters in FP16. This allows fine-tuning a 65B model on a single 48GB GPU — previously impossible even for full fine-tuning of a 7B model.

  • NF4 (NormalFloat4): A 4-bit data type optimized for normally distributed weights. Better than standard INT4 for model weights.
  • Double quantization: Quantize the quantization constants themselves, saving additional memory.
  • Paged optimizers: Use CPU memory for optimizer states when GPU memory is full, swapping pages as needed.

QLoRA achieves only ~1% quality degradation vs full 16-bit fine-tuning, while reducing memory by 4-8×. This has democratized LLM fine-tuning — anyone with a consumer GPU can now fine-tune state-of-the-art models.

Fine-Tuning Data Best Practices

The single most important factor in fine-tuning quality is your data. Architecture matters far less:

  • Quality over quantity: 1000 carefully curated examples beat 100,000 noisy web-scraped examples. Each example should demonstrate the exact behavior you want.
  • Diverse coverage: Cover all the edge cases your model will encounter. If your model will see 10 types of user requests, make sure you have good examples for each.
  • Input-output alignment: The (x, y) pairs must be perfectly consistent. If you fine-tune on (question, answer) pairs, make sure the answer format is identical across all examples.
  • Mix in general data: To prevent catastrophic forgetting, mix 5-20% of general instruction data (like ShareGPT, OpenAssistant) with your domain data.
When NOT to fine-tune: If your use case is "answer questions about my company documents," RAG (retrieval + prompting) is often better than fine-tuning. Fine-tuning teaches the model how to answer, not what to know. Use fine-tuning when you need the model to follow new patterns (format, tone, reasoning style), not when you need it to know new facts.

Connecting Back to minGPT

Everything you learned about minGPT's training loop applies directly to fine-tuning:

  • The same model(x, y) → loss → loss.backward() → optimizer.step() cycle.
  • The same cross-entropy loss, just on a different dataset.
  • The same gradient clipping, learning rate scheduling, and callback mechanisms.
  • The key difference: you start from pretrained weights (much lower initial loss) and use a much smaller learning rate (typically 1e-5 to 5e-5 vs 3e-4 for pretraining).

If you can train a minGPT model from scratch, you already understand 90% of what fine-tuning does. The rest is just infrastructure — LoRA wrappers, quantization, and data formatting.

16. minGPT Implementation Details

minGPT deliberately keeps everything minimal, but real-world production code must handle many additional issues. Below we examine each simplification in depth: what it looks like in minGPT, why industry must add it, and why Karpathy deliberately left it out for teaching.

1. No FlashAttention / memory efficient attention

What is this?
Standard attention explicitly materializes a T×T score matrix when computing Q@K^T (B×nh×T×T for batch and heads). At T=4096 this matrix is already large; at T=32k it blows up memory. FlashAttention uses tiling, fused softmax in SRAM, and avoids writing the full attention matrix to HBM, achieving "IO-aware" computation.

In minGPT (model.py, CausalSelfAttention.forward): 

q, k, v = self.c_attn(x).split(...)
    att = (q @ k.transpose(-2, -1)) * (1.0 / math.sqrt(...))
    att = att.masked_fill(self.bias[:,:,:T,:T] == 0, float('-inf'))
    att = F.softmax(att, dim=-1)
    y = att @ v
Every step produces an intermediate T×T tensor.

Production version: Sequence lengths easily reach 32k~128k+, memory usage drops 3-10× at same batch size. 70B model training on long contexts becomes feasible.

Why omitted? Once you use Flash, you can no longer see "how attention scores are computed" — the core process becomes a black box kernel. Teaching goal: let you see mask, scale, softmax, weighted sum clearly.

2. No mixed precision (BF16 + FP32 master weights)

In minGPT: Entire model is FP32 by default. No autocast, no GradScaler, no master copy.

Production impact: Speedup of 1.5-3×, memory halved (BF16 uses 2 bytes instead of 4). Without it, training 10B+ models is prohibitively slow and A100 tensor cores are wasted.

Why omitted? Mixed precision involves amp, GradScaler, all-reduce precision strategies — pure engineering noise for understanding "next word prediction + gradient descent".

3. No gradient checkpointing

In minGPT: None. Trainer directly calls loss.backward(), PyTorch retains all activations.

Production impact: Allows 2-4× larger batch size or sequence length without adding GPUs. Essential for long-context training.

Why omitted? Recomputation complicates training code and debugging. For understanding "what loss.backward() does", it's a distraction.

4. No ZeRO / FSDP distributed strategies

In minGPT: Just model.to(device) and one optimizer. No concept of "multiple GPUs".

Production impact: Without these, GPT-3 175B, LLaMA 70B would never exist.

Why omitted? Distributed code is extremely complex (communication topology, gradient buckets, parameter rearrangement, fault tolerance). Teaching goal: first understand "what a single Block on a single GPU does".

5. Simple learned position embeddings, no RoPE

In minGPT: self.wpe = nn.Embedding(config.block_size, config.n_embd), then directly tok_emb + pos_emb. No rotation, no extrapolation design.

Production impact: When training at 4k and deploying at 32k/128k/1M, learned embeddings extrapolate poorly. RoPE + YaRN/LongRoPE are standard for modern long-context models.

Why omitted? Learned embedding is most intuitive: position i has a trainable vector. You can clearly see it being added to the token embedding. RoPE's math is beautiful but adds extra burden for first-time learners.

6. No GQA (Grouped Query Attention)

In minGPT: Full independent heads: k = k.view(B, T, self.n_head, hs), no grouping.

Production impact: Inference memory and bandwidth pressure is enormous. LLaMA2/3, Mistral all use GQA/MQA. Without it, 70B model with 128k context would consume all available memory.

Why omitted? GQA mainly affects "KV cache management during generation". minGPT's core teaching goal is "training-time next token prediction + causal attention". Adding KV cache optimization confuses the distinction between training and inference bottlenecks.

Summary of the six simplifications: They keep minGPT's core loop in a few hundred lines of crystal-clear code, but directly prevent it from scaling to billions of parameters. When you want to train a real large model, these "omitted things" immediately become hard engineering problems you must solve.

18. Scaling Laws & Emergent Abilities

In 2020, OpenAI published the seminal paper "Scaling Laws for Neural Language Models". Through extensive experiments, it demonstrated a striking fact:

Language model performance can be predictably described by a power-law relationship between three variables: model size, dataset size, and compute budget.

Core Findings of Scaling Laws

Within a certain range:

  • Increasing model parameters (N), data (D), or compute (C) reduces loss in a predictable power-law fashion.
  • There is an optimal balance between N and D; both should grow together as compute grows.
  • Under a fixed compute budget, it's best to allocate compute evenly between model size and data, rather than stacking only model or only data.

This directly guided the training configurations of GPT-3, Chinchilla, LLaMA, and others.

The chart below shows the classic power-law relationship: as compute budget increases, model loss decreases in a smooth, predictable curve. The key insight from Chinchilla is that under the same compute budget, allocating it optimally between model size and data yields a lower loss than over-allocating to model size alone (as GPT-3 did).

Emergent Abilities

When model scale crosses certain thresholds, entirely new capabilities suddenly appear — like a "phase transition" in physics:

  • Arithmetic: In some evaluations, multi-digit addition and chain reasoning become much stronger at larger scale. This does not mean small models cannot learn arithmetic at all; it means generalization and few-shot behavior are much weaker.
  • In-context learning (few-shot): Beyond a certain scale, providing examples in the prompt significantly boosts performance. Smaller models show minimal improvement from in-context examples.
  • Instruction following: The ability to follow complex instructions emerges around 10-100B parameters.
  • Multilingual ability: Cross-lingual transfer only becomes effective above a size threshold.
  • Code generation: From writing simple scripts to implementing complete algorithms.

These abilities don't improve gradually — they appear abruptly. This is why simply increasing scale can produce qualitative leaps that surprise even the researchers building these models.

Debate around emergence: Some researchers argue that "emergence" is partly an artifact of discontinuous evaluation metrics (e.g., accuracy jumping from 0% to 50% looks like a phase transition, but the underlying capability may improve continuously on a more granular metric). Regardless, the practical effect is real: sufficiently large models can do things that smaller ones simply cannot.

Chinchilla Scaling Laws: The Compute-Optimal Revolution

The original Kaplan Scaling Laws (2020) suggested that to minimize loss, the optimal strategy leaned toward scaling model parameters faster than data. This led to models like GPT-3 (175B parameters, 300B tokens): very large models, but relatively few training tokens by later standards.

But DeepMind's Chinchilla paper (2022) re-examined this question more systematically. They trained 400 models of varying sizes and data volumes, and reached a strikingly different conclusion:

  • Parameters and data must scale together: This does not mean "the number of parameters equals the number of tokens". Under a fixed compute budget, both model size N and training tokens D should grow. A common Chinchilla-style rule of thumb is that training tokens should far exceed parameters, on the order of tens of tokens per parameter.
  • Previous models were undertrained: GPT-3 (175B, 300B tokens) used about 1.7 tokens per parameter; Chinchilla (70B, 1.4T tokens) used about 20 tokens per parameter. The latter has fewer parameters, but each parameter saw much more data.
  • The same compute → better model: Chinchilla used FLOPs close to GPT-3 but achieved significantly lower perplexity, showing that many earlier models had "too much model, too little data".

This finding revolutionized training strategies. Many later models stopped chasing parameter count alone and put much more emphasis on training tokens, data quality, deduplication, and filtering. In practice, a smaller model trained more thoroughly can beat a larger undertrained one.

The Ceiling of Scaling

Scaling Laws only hold within a certain range. Continued scaling faces:

  • Rising marginal cost of high-quality data: public internet text can be repetitive, polluted, or low quality, so further scaling requires stronger filtering, synthetic data, and feedback data.
  • Compute costs grow linearly but returns may diminish.
  • Alignment difficulty increases (larger models more prone to harmful outputs).

minGPT shows us that even at tiny scale, Transformer + next-token prediction can learn simple sequence patterns. The future likely requires "Scaling + better algorithms/data/architecture", not pure scaling.

19. Position Encoding & Long Context Techniques

Why Does Transformer Need Position Encoding?

Self-attention is permutation invariant. Without position information, "I like cats" and "cats like I" are the same to the model.

The original Transformer uses sinusoidal position encoding (fixed). GPT uses learned position embeddings.

From Absolute to Relative Position

  • RoPE (Rotary Position Embedding): Common in models such as LLaMA and PaLM. It encodes relative position into Q and K dot products through rotation.
  • ALiBi: Adds a linear distance-based bias to attention scores, allowing training on shorter sequences than inference.
  • YaRN, LongRoPE: Interpolation/extrapolation of RoPE for 128k+ or even 1M context.

RoPE Deep Dive: Math & Code

RoPE transforms query and key vectors by rotating them in 2D subspaces. For a position p and dimension pair (2k, 2k+1):

R(p) · q = [q₂ₖ·cos(pθₖ) − q₂ₖ₊₁·sin(pθₖ), q₂ₖ·sin(pθₖ) + q₂ₖ₊₁·cos(pθₖ)]
where θₖ = 10000^(−2k/d)

The key property: after applying RoPE to Q and K, their dot product only depends on the relative position (m − n), not absolute positions:

(R(m)·q) · (R(n)·k) = q · R(n−m) · k

This relative-position encoding is better suited to long-context extension than a fixed learned position table. Stable extrapolation to much longer sequences usually still needs matching training strategy or RoPE interpolation/scaling techniques.

Figure 13.1: RoPE Visualized — Vector Rotation in 2D Subspace

The diagram shows how a 2D vector rotates as position increases. Each position p gets a unique rotation angle, and the dot product of two rotated vectors depends only on their angle difference (relative position), not absolute values.

Here's a minimal implementation (real systems usually cache cos/sin):

def apply_rope(x):
    # x: (B, n_head, T, head_size), head_size must be even
    B, n_head, T, head_size = x.shape
    half = head_size // 2

    # Each pair of dimensions forms a 2D plane with its own frequency.
    freqs = 10000.0 ** (-torch.arange(0, half, device=x.device) / half)
    pos = torch.arange(T, device=x.device)
    theta = pos[:, None] * freqs[None, :]  # (T, half)
    cos = theta.cos()[None, None, :, :]    # (1, 1, T, half)
    sin = theta.sin()[None, None, :, :]    # (1, 1, T, half)

    x_even = x[..., 0::2]
    x_odd = x[..., 1::2]
    out = torch.empty_like(x)
    out[..., 0::2] = x_even * cos - x_odd * sin
    out[..., 1::2] = x_even * sin + x_odd * cos
    return out

Unlike minGPT's learned wpe (a simple nn.Embedding lookup), RoPE is baked into the attention computation itself. This makes it better suited to long-context modeling. Combined with YaRN or LongRoPE-style interpolation/scaling, modern models can extend toward 128k and even longer contexts.

Long Context Challenges & Engineering Solutions

Even with good position encoding, ultra-long context (128k+) faces:

  • KV Cache memory explosion (each token stores K and V).
  • Attention sparsity: models actually only focus on a few key tokens.
  • Scarcity of long sequences in training data.

Common engineering approaches:

  • FlashAttention-2/3: drastically reduces memory bandwidth requirements.
  • PagedAttention (vLLM): manages KV Cache like operating system paging.
  • StreamingLLM / sliding window + attention sink: keep only recent window + a few "attention sink" tokens.
  • Ring Attention: distribute sequence chunks across multiple devices in a ring.

These techniques make long-context deployment more feasible, but 128k and 1M-scale contexts still depend heavily on model size, memory, parallelism strategy, and inference framework. It remains a mixed engineering and algorithmic problem.

20. Transformer Limitations & Modern Evolution

Fundamental Problems with Transformer

Despite great success, Transformer has inherent limitations from first principles:

  1. Quadratic complexity: Self-attention is O(n²), memory and compute explode at 128k, 1M context. At n=128k, a single attention matrix is 128k × 128k = 16 billion entries per head.
  2. Fragile position encoding: Despite RoPE, ALiBi improvements, position understanding is "learned" not "built-in" — the model must infer position from pattern rather than having it as a primitive.
  3. Lack of inductive bias: Both a strength (can learn anything) and weakness (needs more data for simple patterns that RNNs could learn with far fewer examples).
  4. Hallucination & factuality: The training objective is "predict the most likely next token", not "be correct". This is the root cause of all hallucination.
  5. KV cache wall: Even with GQA, the KV cache for a 70B model at 128k context is hundreds of GB — beyond most GPUs.

Mamba / State Space Models: How They Work

Mamba (2023) is built on state space models (SSM). Instead of comparing every token to every other token, it maintains a hidden state that evolves over time, similar to RNNs but with a key difference: the state transition is input-dependent (selective), not fixed. This selectivity is what gives Mamba its power — the model can choose what to remember and what to forget based on the current input.

Concretely, a simplified Mamba layer does:

# Mamba-style SSM (highly simplified)
h = torch.zeros(hidden_size)  # state: fixed size, no growth
for x_t in input_sequence:    # sequential scan
    A = compute_A(x_t)         # input-dependent state transition
    B = compute_B(x_t)         # input-dependent projection
    h = A @ h + B @ x_t        # state update (like RNN)
    y_t = C @ h                # output from state
# Total memory: O(hidden_size), not O(n²)

The advantage: no KV cache, O(n) memory, and the hidden state can theoretically capture infinite context. The tradeoff: Mamba lacks the global "look anywhere" ability of attention — information must flow through the state sequentially, which can make tasks requiring long-range retrieval (e.g., "find the needle in the haystack") more difficult.

On standard NLP benchmarks, similarly sized Transformers still slightly outperform Mamba, but Mamba dominates on long-sequence efficiency. The gap is narrowing with each new SSM variant (Mamba-2, H3, etc.).

Hybrid Architectures: Getting the Best of Both

A rapidly growing trend is to combine Transformer and SSM layers. Typically, every Nth layer is an attention layer (for global retrieval), and the rest are Mamba layers (for efficient sequence processing). Examples:

  • Jamba (AI21 Labs): Alternating attention + Mamba layers, with Mixture-of-Experts for FFN.
  • Zamba: Shared attention layer across blocks + Mamba layers.
  • Samba: Interleaved Mamba + sliding window attention.

These hybrids aim to preserve the "needle-in-haystack" retrieval capability of attention while keeping the O(n) efficiency of SSMs for most of the computation.

What Hasn't Changed

Despite all these innovations, the vast majority of production systems today are still based on Transformer decoders. The core ideas — next-token prediction, attention, residual connections, normalization — remain central to the field. Even hybrid models use attention for the most critical layers. The question is not "will attention be replaced?", but "how much of the computation can be done more efficiently without sacrificing quality?".

21. Hallucination, Alignment & Future Directions

Why Do LLMs Hallucinate?

Hallucination is not a bug; it's a feature of the training objective. The model is trained to produce the most likely next token, not to be factually correct. From first principles:

  • The model has no internal "truth database" — it only has statistical patterns.
  • When faced with ambiguous or rare knowledge, it defaults to "the most common pattern in training data", which may be inaccurate.
  • The autoregressive nature means errors compound: one wrong token can lead to an entirely fabricated narrative.

Concrete Example: How One Wrong Token Cascades Into Hallucination

Consider the question: "When was the Eiffel Tower built and who designed it?"

The correct answer is: "The Eiffel Tower was built between 1887 and 1889, designed by Gustave Eiffel."

Now imagine the model generates the first few tokens slightly wrong:

Correct path: The Eiffel Tower was built between 1887 and 1889, designed by Gustave Eiffel.
↓
Slightly wrong: The Eiffel Tower was built in 1867 ...
↑ Just one wrong token (1867 instead of 1887). Now the model must continue from this incorrect fact.
↓
Cascade begins: "for the 1867 World Exposition ..."
The model generates a plausible-sounding fact: 1867 was indeed a World Exposition in Paris. But this is factually wrong — the Eiffel Tower had nothing to do with the 1867 Exposition.
↓
Elaboration: "... designed by Jean-Charles Alphand to celebrate the Second French Empire..."
The model generates increasingly specific (and fabricated) details. Each token locks in the wrong historical narrative. By now, it's impossible to recover.

Why this happens: The model has no internal "truth database" to check against. It only knows "given the previous tokens, what token is most probable?" Once 1867 is chosen — because it shares statistical patterns with 1887 (both are 4-digit years, both appear frequently in Paris history contexts) — the model commits to a branch where 1867 is treated as fact, and all subsequent tokens are conditioned on this false premise. This is autoregressive error compounding — the core mechanism behind hallucination.

Why it's hard to fix: The model's own training objective (next token prediction) provides no mechanism for "fact-checking." It would need an external knowledge base, retrieval augmentation (RAG), or a separate verification step — none of which are part of the core autoregressive loop. This is why hallucination is considered an open research problem, not a simple bug.

Alignment: RLHF, DPO, Constitutional AI

Alignment techniques aim to make model outputs match human values and preferences:

  • RLHF (Reinforcement Learning from Human Feedback): Train a reward model on human preferences, then use PPO to fine-tune the LLM to maximize reward.
  • DPO (Direct Preference Optimization): Skip the reward model and directly optimize from preference pairs.
  • Constitutional AI: Use a set of principles (a "constitution") to self-critique and revise outputs.

Figure 15.1: RLHF Alignment Pipeline

RLHF (Reinforcement Learning from Human Feedback) is a three-stage process that aligns model outputs with human preferences. The reward model acts as a "human preference proxy" — it learns what humans prefer, and PPO trains the base model to maximize this reward signal.

RAG (Retrieval Augmented Generation)

Instead of storing all knowledge in model parameters, RAG retrieves relevant documents from a knowledge base at inference time and conditions generation on them. This reduces hallucination and makes updates easy (just update the knowledge base).

Practical Techniques for Reducing Hallucination

Beyond the high-level methods above, here are concrete, immediately actionable techniques for reducing hallucination in practice:

1. Prompting Strategies

  • Chain-of-thought (CoT): Ask the model to reason step by step before answering. This exposes intermediate reasoning and reduces the chance of jumping to incorrect conclusions. Example: "Let's think step by step: first, ..."
  • Self-ask / verification: Prompt the model to explicitly identify what it knows vs. what it's unsure about. "Only answer if you're confident. If unsure, say 'I don't know'."
  • Citation requirement: Ask the model to cite sources for factual claims. Even if the citations are made up (a known problem), the act of "pretending to cite" forces the model to be more specific, which actually reduces hallucination rates.
  • Grounding prompt: "Based only on the following context, answer the question. If the context doesn't contain the answer, say so." This is the foundation of RAG.

2. Sampling and Decoding Strategies

  • Lower temperature: temperature=0.1-0.3 makes the model more deterministic and less likely to invent creative (but false) details. Temperature > 1.0 dramatically increases hallucination.
  • Top-p (nucleus) sampling: p=0.9-0.95 focuses sampling on the most probable tokens, reducing the chance of picking an unlikely (hallucinated) path.
  • Do not sample (greedy decoding): Use do_sample=False or argmax for the most conservative output. Note: minGPT's generate divides logits by temperature directly, so do not set temperature to 0.
  • Contrastive decoding: Compare the output of the target model with a smaller "amateur" model. Tokens that the amateur also finds likely are suppressed, encouraging the expert to use its deeper knowledge rather than surface patterns.
  • Self-consistency: Generate multiple answers (e.g., 5 with temperature=0.3) and take the majority vote. If 4 out of 5 agree, the answer is likely reliable. If they disagree, you know the model is uncertain.

3. Post-hoc Verification

  • Self-check: After generating an answer, ask the same model: "Is the above answer factually correct? List any potential errors." This leverages the model's own knowledge to catch its mistakes — it sometimes "knows better" than it generates.
  • External fact-checking: For claims about specific entities, use a search engine or knowledge base API to verify each factual statement after generation. Tools like Google Fact Check Tools or custom retrieval can catch errors.
  • Cross-model verification: Ask two different models (e.g., Claude + GPT-4) the same question. If they agree, confidence is higher. If they disagree, investigate further.
  • Uncertainty estimation: Monitor the model's token probabilities. If the probability of the first token is low (<0.5), or the entropy of the logits is high, the model is "uncertain" — flag these outputs for human review.

4. Training-Time Techniques

  • Contrastive learning on hallucination data: Construct pairs where one response is factual and the other is a hallucinated version of the same question. Train the model to prefer the factual response via preference optimization (DPO).
  • Hallucination-aware data augmentation: In the fine-tuning dataset, deliberately include examples where the correct answer is "I don't know" or "This information is not available." This teaches the model that admitting ignorance is acceptable.
  • Rejection sampling: During RLHF/DPO training, generate multiple responses per prompt and have human raters score them. Only train on the highest-quality responses. This naturally reduces hallucination because hallucinated responses get low scores and are excluded from training.

5. Architectural Approaches

  • Built-in retrieval: Models like Retro (RETrieval-augmented Transformer) have retrieval as part of the architecture — every token generation step can attend to retrieved documents from a database. This is more tightly integrated than pre-pending context.
  • Tool-former architectures: The model is trained to output structured tool calls (e.g., {search: "capital of Mongolia"}) when it encounters factual uncertainty, rather than generating from memory. The tool result is then fed back into the context.
  • Verification heads: Add a secondary classification head to the model that predicts "is this generation likely factual?" This can be trained with contrastive examples and used to flag or reject uncertain outputs at inference time.
Summary: There is no single "fix" for hallucination. The best approach combines: (1) prompt engineering to constrain the model's generation space, (2) careful sampling parameters that favor conservative outputs, (3) post-hoc verification to catch errors, and (4) training techniques that explicitly penalize hallucination. For production systems, RAG + low temperature + self-check provides the best reliability-to-effort ratio.

Alignment Side Effects and Risks

Alignment techniques make models more "helpful" and "harmless", but introduce new challenges:

  • Over-refusal: Models become overly cautious, refusing harmless requests.
  • Alignment tax: Alignment reduces raw capability on certain benchmarks (the model becomes "safer" but "dumber").
  • Reward hacking: Models learn to "please" the reward model rather than genuinely understanding human intent.

This shows that alignment itself is an open research problem, far from solved.

Modern LLMs are increasingly used as agents that can call external tools: calculators, code interpreters, search engines, APIs. This shifts the model from "knowing everything" to "knowing how to find out", dramatically expanding capability while reducing hallucination.

Future Directions

  • Test-time compute scaling (chain-of-thought, self-consistency, tree-of-thought).
  • Long-form factuality and multi-hop reasoning.
  • Multimodal understanding (text + image + audio + video).
  • Embodied AI: connecting LLMs to robotic control.

Chatbot Arena: Human Preference Ranking

The Chatbot Arena (by LMSYS) is currently the most influential LLM leaderboard. It works differently from benchmarks:

  1. Blind A/B comparison: A user submits a prompt. Two anonymized models generate responses. The user votes for which response is better (or declares a tie).
  2. Elo scoring: Inspired by chess rankings. Each model has an Elo rating. When model A beats model B, A gains Elo points and B loses them. The point change depends on the rating difference — beating a much weaker opponent gains few points; beating a much stronger opponent gains many.
  3. Bootstrapped confidence intervals: Ratings include uncertainty estimates. A model rated 1250±15 is meaningfully different from 1200±10 only if the confidence intervals don't overlap.
  4. Style vs quality control: Arena ratings are filtered to separate "style" preferences (formatting, verbosity) from "quality" (accuracy, helpfulness). Models that are more verbose often score higher even if their factual accuracy is similar.
Elo_new = Elo_old + K × (S - E)

Where K is the maximum adjustment per game, S is the actual result (1 for win, 0.5 for tie, 0 for loss), and E is the expected score based on rating difference.

Automated Evaluation: LLM-as-Judge

Running human evaluation at scale is expensive. A common alternative is using a strong LLM (like GPT-4) as an automated judge:

  • Pairwise comparison: "Given the instruction, which response is better? A or B?" The judge LLM scores A vs B directly.
  • Absolute scoring: "Rate this response on a scale of 1-5 for helpfulness." The judge LLM assigns a numeric score.
  • Rubric-based: "Check if the response satisfies each of these 5 criteria." The judge follows a detailed scoring rubric.

Issues with LLM-as-Judge: Position bias (prefers first or second response), verbosity bias (prefers longer responses), self-enhancement bias (prefers its own style), and rubric overfitting. Despite these, LLM-as-Judge correlates reasonably well with human judgment (0.5-0.7 Spearman correlation) and is widely used for rapid iteration.

Key Benchmarks: How to Read Them

When reading model leaderboards, keep these limitations in mind:

  • Benchmark contamination: If the model was trained on data that includes the test set, benchmark scores are meaningless. This is a widespread problem — many models have seen MMLU examples during training.
  • Overfitting to benchmarks: Models can be optimized for specific benchmarks without improving general capability. A model trained to ace MMLU may still fail at simple reasoning tasks not in the benchmark.
  • Saturation: Top models now achieve >90% on MMLU and >95% on HumanEval. These benchmarks no longer differentiate between the best models. New, harder benchmarks are constantly needed.
  • Multidimensional evaluation: A single "overall score" hides important tradeoffs. A model that scores high on coding benchmarks may score low on safety. Always look at the breakdown.
Practical advice: For choosing a model for your use case, don't rely on a single leaderboard score. Test 2-3 top models on a small set of your own real-world examples. Benchmark scores are useful for filtering (is this model in the right ballpark?) but not for final selection (which model is best for my specific task?).

The Elo Rating System in Detail

Since Elo is used by both Chatbot Arena and many coding agent platforms, understanding its math helps interpret ratings:

  • Expected score: E = 1 / (1 + 10^((R_B - R_A) / 400)). A 400-point difference means the stronger player is expected to win ~10× more often.
  • K-factor: Controls how quickly ratings change. High K (32+) = fast adaptation but noisy. Low K (4-8) = stable but slow to reflect true skill. Chatbot Arena uses K=4 for established models to reduce volatility.
  • ELO ≠ absolute quality: Elo is relative, not absolute. A model with 1250 Elo in the Arena may be worse than a model with 1100 Elo in a different evaluation pool, because Elo depends on the opponent pool.

From minGPT's "pure model" to Claude Code, Codex CLI and modern coding agents.

2. How is Long-term Memory Implemented?

An LLM conversation is still fundamentally bounded by the context window. "Long-term memory" usually does not involve writing information into model parameters; it's an external memory system:

  1. Extract: Distill stable information from historical conversations, user corrections, project files, and execution results.
  2. Store: Write to local files, databases, vector stores, configuration files, or cloud user profiles.
  3. Retrieve: On new tasks, select relevant memories based on project, path, keywords, embedding similarity, or rules.
  4. Inject context: Put retrieved memories into system/developer/tool context for the model.
  5. Update & clean: Outdated, conflicting, or incorrect memories need to be overwritten, merged, or deleted.

This is completely different from minGPT training. minGPT updates weights through backpropagation; a coding agent's long-term memory is typically preserved across sessions through external state. The model "appears to remember" because the system retrieves relevant memories and places them back into the context on the next startup.

3. Claude Code's Memory & Rules Layer

Claude Code's documentation divides project memory into two types: persistent instruction files written by the user (e.g., CLAUDE.md), and automatic memories written by the tool based on corrections, preferences, and project discoveries. Both are loaded as context on new sessions — but they are still not part of the model weights.

This is a crucial point: CLAUDE.md is more like a "project manual + team rules"; automatic memories are more like "pitfalls I stepped into last time in this repo". To forcibly prevent dangerous actions, you should rely on hooks, permissions, and tool policies, not just a natural language rule.

5. Context vs System Prompt: What's the Difference?

Context is all the input material the model can see in a single invocation. It's like "the full set of exam materials and references given to the model", potentially including system prompts, developer instructions, user questions, conversation history, project file snippets, retrieval results, long-term memories, tool outputs, error logs, screenshot descriptions, etc.

System prompt (system instructions) is a special part of the context, usually placed at the highest priority position, used to define the model's identity, boundaries, style, safety rules, tool usage principles, and answer format. It is not the entire context — it's the layer that serves as the "master rules" within the context.

In this example, only the first block is the "system prompt". The entire package together is the "context". Long-term memory is not the system prompt itself — it is retrieved by the CLI/App and placed into the context; the system prompt governs how the model should use this information.

Connecting Back to First Principles

Everything we've learned about minGPT — next-token prediction, attention, training dynamics — is directly relevant to understanding how coding agents work. The agent's "reasoning" is just the LLM generating tokens conditioned on a carefully crafted context. The agent's "tool calls" are just special tokens that the model outputs, which the system interprets as commands.

Understanding the fundamentals of GPT gives you a massive advantage in building, debugging, and improving agent systems. The "predict → score → adjust" cycle from minGPT's training loop is mirrored at the agent level as "act → observe → replan".

Skills and subagents: when to use them

Skills are reusable workflows. Use them when your team repeats the same sequence: release prep, code review, dependency upgrade, docs sync, security checklist, or API migration. Keep each skill focused and explicit about when it should or should not trigger.

Subagents are isolated workers. Classic Project Walkthroughs

projects/adder: Teaching GPT to Add Numbers

This is the most instructive example in minGPT. It shows how to train GPT from scratch on an algorithmic task.

Dataset design insight: The answer is encoded in reverse order (least significant digit first). This aligns the autoregressive prediction order with the natural computation order of addition (right-to-left carry propagation), dramatically reducing learning difficulty.

Loss is computed only on the answer part (using ignore_index=-1), forcing the model to learn the algorithm rather than memorize.

projects/chargpt: Character-Level Language Model

Trains GPT on any text file at the character level. This is the simplest way to see language modeling in action:

  • Vocabulary: all unique characters in the text (much smaller than BPE).
  • Training: next character prediction.
  • Generation: sample character by character.

Despite its simplicity, chargpt exhibits all the core patterns of large language models: context learning, coherent generation (up to a point), and the ability to capture text style and structure.

Lab 2: Forward Pass + Shape Tracing (The Most Important Run)

Code Example Create random input, run forward, print shapes 
x = torch.randint(0, config.vocab_size, (2, 16)).to(device)
print("Input shape:", x.shape)          # (2, 16)

Input shape: torch.Size([2, 16]) ✓ Forward pass complete! Logits shape: torch.Size([2, 16, 50257])
Key observation:
We created 2 sentences, each with 16 tokens.
After forward pass, logits shape is (2, 16, 50257).
This means: for the last position of each sentence, the model scores all 50,257 possible next words.
Higher score = model thinks that word is more likely here.
Remember: Throughout intermediate layers, the shape stays (batch, seq_len, n_embd). Only the final lm_head step transforms it to (batch, seq_len, vocab_size).

Lab 3: Peek Inside the Model with Forward Hooks

Code Example Register forward hooks to inspect embedding / first & last Block / lm_head statistics 
activations = {}
def make_hook(name):
    def hook(m, inp, out):
        t = out[0] if isinstance(out, tuple) else out
        activations[name] = t.detach().cpu()
    return hook

hooks = []
hooks.append(model.transformer.wte.register_forward_hook(make_hook('embedding')))
hooks.append(model.transformer.h[0].register_forward_hook(make_hook('first_block')))
hooks.append(model.transformer.h[-1].register_forward_hook(make_hook('last_block')))
hooks.append(model.lm_head.register_forward_hook(make_hook('lm_head')))

_ = model(torch.randint(0, 50257, (1, 8)).to(device))
for n, a in activations.items():
    print(n, a.shape, 'mean/std', a.mean().item(), a.std().item())

Lab 4: Train with Trainer on a Minimal Dataset (Sort / Count Pattern)

Below demonstrates how to subclass Dataset and hand it to the Trainer (inspired by demo.ipynb's SortDataset + learning_guide.ipynb's simple pattern).

Code Example Minimal dataset + Trainer training for 50 steps 
from torch.utils.data import Dataset
class SimplePatternDataset(Dataset):
    def __init__(self, n=100, seq_len=8):
        self.n, self.seq_len = n, seq_len
    def __len__(self): return self.n
    def __getitem__(self, i):
        x = torch.arange(self.seq_len) % 5
        y = (x + 1) % 5
        return x, y

train_dataset = SimplePatternDataset(100, 8)
model_config = GPT.get_default_config()
model_config.model_type = 'gpt-nano'
model_config.vocab_size = 5
model_config.block_size = 8
model_small = GPT(model_config)
model_small.to(device)

trainer_cfg = Trainer.get_default_config()
trainer_cfg.max_iters = 50
trainer_cfg.batch_size = 8
trainer_cfg.learning_rate = 6e-4
trainer_cfg.num_workers = 0
trainer = Trainer(trainer_cfg, model_small, train_dataset)
trainer.run()

Key observation:
The pattern is: 0→1, 1→2, 2→3, 3→4, 4→0. The model learns to "count" after just 50 steps!
This proves that the next-token prediction objective can easily capture modular arithmetic, even with tiny models.
The loss drops from 1.6 to 0.34 — not yet perfect (which would be ~0), but clearly learning.
